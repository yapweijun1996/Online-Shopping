# Docker deployment and data boundary

**Current self-hosted deployment:** see [OrbStack + PostgreSQL + Cloudflare Tunnel](ORBSTACK_DEPLOY.md) for the new two-hostname stack. The sections below describe the retained SQLite stack and historical release gates. See [README](../README.md) for local startup. This document records the chosen deployment shape and gates, not a claim that a public host exists.

## Topology

`frontend` is Caddy with only `public/` and a Caddyfile in its image. It serves `/shop/` and `/seller/` as separate PWA scopes and forwards `/api/*`, `/health`, and `/ready` to `backend` on the private Compose network. Its local default binds only loopback. `backend` is one Node 24 API process with private SQLite v5 in the persistent `db_data` volume. Seller session hashes, product image bytes, order contacts, addresses, snapshots, idempotency records, and audit events live there. No SQLite port or backend HTTP port is published. Caddy's `caddy_data` volume preserves TLS state when a real HTTPS hostname is configured.

The backend accepts a trusted `X-Real-IP` only in this private-proxy topology. Caddy overwrites the incoming header with its direct client address. Do not expose backend port 3000 or add untrusted containers to the private network. If a load balancer or Cloudflare Tunnel is added in front of Caddy, set `CLIENT_IP_SOURCE={header.CF-Connecting-IP}` in the Compose environment file (default `{remote_host}`) so limits apply per visitor, and only when Caddy is reachable solely through that path. Scale the backend at one instance: the SQLite file is a single-writer store. Login and checkout limits are stored in the database (`rate_limit_attempt`, hashed client keys) and survive restarts.

## Secrets and startup

The operator supplies an ignored file at `ADMIN_PASSWORD_FILE_HOST` (default `.local/admin-password`), mounted as a Compose secret at `/run/secrets/admin_password`. The backend reads it as nonroot, validates it, and creates the first seller account (the Owner) on a database that has no accounts. After that the accounts in the database are the truth: the secret is only a bootstrap value, a changed secret is ignored, and the Owner changes the password in the app (Account, Change password). If the Owner password is lost, run on the server `docker compose exec -e NEW_SELLER_PASSWORD='<temporary, 12+ characters>' backend node scripts/reset-seller-password.js <username>`; it ends that account's sessions and forces a new password at the next sign-in (except on a quick sign-in site, where passwords cannot be changed and the temporary password simply stays). `ADMIN_USERNAME` is also required. Do not print either secret or copy it into the image, `.env.example`, frontend files, logs, or Git. Production requires `NODE_ENV=production`, an exact HTTPS `PUBLIC_ORIGIN`, a private `DB_PATH`, and a strong non-placeholder password. The local default is development mode on loopback; it is not appropriate for real contacts.

## Integration master key

Credentials a seller saves for WhatsApp or a courier are stored encrypted (AES-256-GCM, `src/secret-box.js`). The master key file is an ignored host file at `INTEGRATION_KEY_FILE_HOST` (default `.local/integration-keys`), mounted as the Compose secret `integration_keys` and read through `INTEGRATION_KEY_FILE`. Each line is `id=<32 random bytes in base64>`; the first line is the active key, so a key is rotated by adding a new first line, re-encrypting the rows, then removing the old line. Create it once with `printf 'k1=%s\n' "$(openssl rand -base64 32)" > <path>` and `chmod 600`, and keep a copy apart from database backups: losing the key makes every stored credential unrecoverable. If the file is configured but missing or malformed, the backend refuses to start, so the deploy health check fails and the previous release stays in service.

## Data lifetime and release gate

The owner requires **permanent retention of submitted orders, including names, phones, and addresses**. The current API has no order/contact/address deletion endpoint or automatic server retention job; an authorized `DELETE` request returns 404 and leaves the order intact. Restarting containers preserves SQLite data in `db_data`. This is the current application rule. A privileged database operator can still alter or destroy the file, and local backup alone cannot guarantee permanent recovery. The optional browser input-suggestion history is separate: it is user-controlled, clearable, and expires after 90 days.

Official tax guidance requires retaining business records for minimum periods: [Singapore IRAS says at least five years from the relevant Year of Assessment](https://www.iras.gov.sg/taxes/corporate-income-tax/basics-of-corporate-income-tax/record-keeping-requirements), and [Malaysia LHDN says digital-business records for seven years](https://www.hasil.gov.my/syarikat/perniagaan-digital/). These sources do not by themselves establish that every buyer/recipient phone and address must remain identifiable forever. [Singapore PDPA section 25](https://sso.agc.gov.sg/Act/PDPA2012?ProvIds=P16-) limits retention once the original purpose and legal/business need end; [Malaysia's Personal Data Protection Standard](https://www.pdp.gov.my/ppdpv1/wp-content/uploads/2024/07/LatestStandard.pdf) says to keep personal data no longer than necessary unless another legal provision requires it. The exact obligations depend on the operating entity, transactions and applicable laws.

**Owner decision (2026-09-26):** the owner recorded the retention basis as business/contractual necessity — order records support dispute resolution, warranty/after-sales claims, and an audit trail for as long as the seller offers products and support, not customer consent. This is the owner's own compliance judgment, not an independent legal review; it does not itself prove indefinite retention is lawful in every jurisdiction the business operates in, and the owner remains responsible for revisiting it if the operating entity, countries served, or applicable law change. Keep the no-delete application rule. Restrict operator and backup access, and define correction and recovery procedures. Do not add an automatic order purge or a database rule that would prevent a legally required correction or disposal.

`docker compose down -v` removes named volumes and must not be used as a routine stop. Pin a Compose project name so volume identity remains stable. Before any upgrade or schema migration, take a recoverable, access-restricted backup of the entire SQLite volume while the backend is stopped, including any WAL/SHM files; test restore into an isolated Compose project before relying on it. Define backup frequency, encryption, storage location, access, restore time, and retention with the owner. The repository has not yet verified a production backup/restore or rollback.

For local use, [backup.sh](../deploy/backup.sh) takes an optional environment-file path and Compose project name (`.local/docker.env` and `online-shopping` by default). It first confirms the existing `db_data` volume and backend image, stops both containers, archives the entire volume with `0600` file mode under ignored `.local/backups/`, verifies that the tar can be listed, records a SHA-256 checksum, and restarts the stack even after an archive failure. It refuses to manufacture an empty backup for a missing volume. The archive is **not encrypted**; treat it as sensitive data and do not copy it to public storage. Preserve its file permissions and verify a recovery on a fresh volume before depending on it. Do not restore over a live or existing database volume.

An isolated synthetic-data rehearsal backed up a stopped test volume, recorded a SHA-256 digest, and restored its database, WAL and SHM files into a new Compose project's empty volume. The restored API returned the original active product, order number, buyer contact, destination and audit event. The test instance was stopped without deleting its volume. The default clean local stack was separately backed up with `backup.sh`; its archive listed all three SQLite files, remained `0600`, and the stack returned healthy. This proves a local recovery path for the tested schema and image only. Production encryption, off-host copy, schedule, retention, restore-time target, and rollback still need a decided and verified plan.

For the local v3→v5 upgrade, the backend was stopped and its `/data` directory copied to restricted ignored storage. The copied database passed `PRAGMA integrity_check` with 20 demo products and zero orders. A separate copy upgraded to v5 with the same 20 products, six category codes, zero orders, `integrity_check=ok`, and zero foreign-key violations before the running stack was rebuilt. A separate automated v3 fixture with an existing order upgraded to v5 with its amount, item currency, idempotency record, integrity and foreign keys intact. The live `/ready` endpoint then returned ready. This validates the tested local data and migration paths; it does not establish a production restore/rollback process.

## Local evidence and outstanding release checks

With a synthetic ignored secret and test order, the two pinned-base images built and started. `/ready`, both PWA assets, proxy API, seller authorization, product create/public visibility, guest order and idempotent replay passed through Caddy. The private SQLite file and secret were mode `0600` under the nonroot backend user. The frontend image lacked backend source/private files and the backend image lacked `public/` and `sample/`. After restarting the backend, the product and order remained; spoofed incoming `X-Real-IP` values did not bypass the login limiter. Missing/weak production credentials exited with status 1. Local backup/restore evidence is recorded above. These are local checks only.

The exact hostname (Cloudflare `*.workers.dev` subdomain, see below) and the lawful basis for permanent retention are now recorded; still settle backup/restore and rollback for the Durable Object data, production secret management, and target-browser PWA installation/update before a public release.
