# WhatsApp Cloud setup UI

Implemented in `public/seller/whatsapp-connection.js`, with localized copy in `whatsapp-cloud-copy.js` and evidence projection/validation in `whatsapp-cloud-state.js`. This is a frontend presentation change over the existing seller connection API. Provider protocol, API routes, credentials-at-rest, session/CSRF checks, rate limits and database schema are unchanged. The QR card remains a separate provider UI.

The card opens on Production. Production and Sandbox retain distinct forms and unsaved drafts in page memory; switching environment, expanding steps or changing language does not save or transfer credentials. Four numbered navigation controls lead to independently expandable Meta app, API credentials, Webhook and Templates cards. Native summary/keyboard expansion also updates the active navigation item. Numbers identify steps, not completion percentages. Opening Meta, typing, revealing or copying never verifies a step. The initial card opens API credentials for an unconfigured connection, or Webhook for an existing connection.

The overview separates the connection DTO's last credential-check time from the current page's explicit readiness-result time. A new page has no retained readiness result. Loading, unavailable service, read errors and forbidden access remain visible with appropriate retry/prerequisite guidance; unreadable state is unknown, not disconnected. Last known connection data is retained across failed reads. Permission loss clears page-owned secret/verification-token values and disables writes. Unauthorized responses use the existing login cleanup.

## API and evidence boundaries

The four raw credential values go to the existing environment-specific PUT. Client assistance matches existing bounds: token20–512 and App Secret16–128 characters without whitespace/control characters; both IDs are5–32 ASCII digits kept as strings. No trimming or partial-secret update is introduced. Updating still requires all four inputs. Successful responses clear secret inputs and hydrate IDs and the saved masked hint. Rejected/invalid writes retain the draft and prior connection. One Cloud operation is allowed at a time; duplicate submits and environment switching during pending writes/checks are disabled.

The Meta link uses the stable official Developers apps entry point. The guide avoids promises about fixed app-type menus or token permanence. Meta controls token validity, app permissions, assets and current setup screens.

Webhook settings use the actual callback URL and connected DTO Verify token. Before connection the card offers a prerequisite instead of a generated token. Independent copy controls report success only after Clipboard API success; denial reveals/selects the actual readonly field for manual copying. Configuration instructions distinguish the Verify token from App Secret. Callback-handshake completion is not persisted by the current backend and is not claimed here.

Readiness runs only after an explicit button in Webhook or Templates. Both invoke the same existing environment-specific GET and share operation/sequence guards. There is no provider polling on load, environment switch, navigation, expansion or locale change. Phone ownership, some-app subscription and signed-webhook App Secret evidence stay separate. A subscribed app is not proof of the intended app. App Secret only passes when the backend supplies signed-webhook proof; entering/storing a secret cannot establish it. Missing, malformed, duplicated or incomplete evidence remains unknown. No UI check establishes billing, registration, messaging authorization or handset delivery.

Template records and counts come from the returned readiness DTO. The UI does not reproduce the backend's expected-template/language algorithm. Empty/malformed/duplicate-identity records or a PASS contradicted by returned non-approved records cannot show a verified template step. Returned UNKNOWN remains UNKNOWN rather than being converted to MISSING. The expandable matrix preserves every returned record, including language codes and literal template names. The existing four template examples and variables remain an explicitly labeled reference, not approval evidence.

## Lifecycle and privacy

Company settings composes Cloud `dispose`, `isBusy`, `hasUnsavedChanges` and a numeric revision signature alongside the existing settings/AI/QR behavior. Secret inputs, including after reveal, and the readonly Verify token opt into private draft revisions. No credential value enters draft signatures, storage, URLs, progress markers, status messages or analytics.

Operation/page/session identities reject stale load, write, readiness and clipboard completions. A field's pending clipboard identity remains disabled across render, reveal and environment changes. Disposal clears page-owned secret inputs, Verify token, pending body references and clipboard-snapshot references, removes the card and aborts/resolves its owned disconnect confirmation. The browser network/clipboard implementation may already hold its own submitted argument; page cleanup does not promise heap zeroing, revocation of a network write, or clearing the OS clipboard. Successful results after leaving cannot remount or populate the old page.

## Verification and limits

Baseline local browser DTO fixtures reproduced the expanded guide pushing the first credential to about1725px at390px and1157px at1920px. The old card measured about2552/1398px high respectively. New initial-view screenshots and geometry check that credentials appear within the first1000px viewport, with long template records remaining within page width.

Focused pure-state tests precede UI integration and cover unavailable/disconnected/unknown/partial/failing/passing evidence, contradictory template records, environment/rotation invalidation and exact validation bounds. Real Chrome UI tests cover390/768/1280/1920px, OS light/dark preferences, an actual alternate light palette, seven locale refreshes, keyboard step navigation, independent draft retention, exact request payload/environment, operation guards, clipboard fallback/races, retry/error/permission/unauthorized paths, disconnect confirmation and stale/disposed results. These are explicitly local UI DTO fixtures, not a real Meta connection or handset-delivery test. Existing backend readiness/API, QR and Company settings tab regressions are checked separately. No full root application suite is run for this change. Production provider/account acceptance requires separately authorized live credentials and is not established by these screenshots.
