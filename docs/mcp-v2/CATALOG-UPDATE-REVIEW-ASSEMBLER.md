# Pure existing-product UPDATE review assembler

`buildCatalogUpdateReviewManifest({snapshot,beforeGraph,projection,reviewLabels,plannedIdentity,baseRevision,codecDigest})` in `catalog-media-review-manifest.js` returns frozen `{manifest,revision,reviewBinding}`. It is a data conversion boundary, not a database reader, business planner, authority callback or write adapter. No engine, flag, registry, scope, policy writer, seller approval or CREATE support is activated by this module.

Inputs are the fresh B1 snapshot, `readCatalogMediaBeforeGraph` result, B2 `projectCatalogMediaMove` result, and complete literal labels from the shared catalog UPDATE state. `baseRevision` is the shared C1b composite computed with the exact immutable normalized intent and planned identity. The caller must acquire the existing platform/store fence, check live authority, and recompute these facts when required. Raw B1 snapshots and byte-loader identities are preserved.

The assembler compares all current graph records by complete ID and value, without assigning meaning to the order in which separate listing records were collected. Ordered gallery associations and ordered private views remain semantic. Both PRODUCT ID sets and the full label table must match. BEFORE literals must equal the actual snapshot SKU/name; all physical own-main keys remain unchanged for this catalog UPDATE subset. AFTER labels are supplied by the shared prepared state; this module does not duplicate shared-field adoption, option clearing, derived labels, currency, uniqueness or stock rules.

For a new private listing, `plannedIdentity` is the strict C1a `{productId,previousListingId,targetCode,newListingId}` context. Product/source/code must match the fresh target plan, which must still represent creation with null ID. Only the one target product's null listing and the one private LISTING record are mapped to that server UUID. Existing target plans cannot receive an identity, other products cannot move, unknown target listings cannot be adopted, and missing/extra removed-listing IDs are rejected. Actual code/UUID absence is established by C1b and rechecked by C1a at application; this pure function cannot prove database absence.

The immutable PRODUCT state preserves physical own-main metadata and derives `ownMainVisible` solely from the verified BEFORE/AFTER views. It validates the view role, holder, visible order and main key against each listing graph. It does not reimplement SHA suppression or gallery selection. Created LISTING records have null BEFORE; removed source listings have null AFTER. Existing products have both states. All C metadata uses the shared projection composite and label binding from `catalog-media-review-wire.js`.

Only old seven-field asset references from the captured source set are eligible. Assets are filtered to the complete physical-main/gallery key union actually used by the BEFORE/AFTER effects; hidden unused physical assets remain in the raw revision and physical budget but are not spuriously presented as required image proof. Shared-main copies retain their original before-owned content reference; private copy aliases are bound in the complete view hash and never passed as fabricated stored asset UUIDs. STAGE references and new-upload bytes are rejected.

The shared byte mapper validates both real physical sides at no more than 16 MiB, then uses conservative `oldBytes=max(beforeOldBytes,afterOldBytes),newBytes=0`. Private projection costs still include the actual full image and thumbnail copy increment separately. The existing 300-product/two-listing/32-old-asset/512-record/16-page limits are retained. Oversize inputs fail closed with controlled 503; no graph or image proof is truncated.

Verification uses actual SQLite/PostgreSQL product services for existing-target adoption, source deletion, copy+thumbnail costs, private planned-ID creation, source shrink, hidden-own-main suppression, SKU holder changes and ten-shared-plus-own-eleven views. Expected AFTER literals are obtained independently by running the real service in a rolled-back transaction. The final actual apply uses the same services and history wrapper and is compared against the assembled physical/visibility effects. Closed-input negatives do not create operations or domain/history writes. A separately labelled synthetic 300-product metadata test verifies complete record/page bounds; it does not establish live authority, native decoding or human approval.
