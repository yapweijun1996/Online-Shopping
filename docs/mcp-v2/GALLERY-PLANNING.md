# Read-only gallery planning extraction

Status: local business-service extraction from `f7dc171`; no MCP media tool, registry/auth change, migration, staging write or production activation. Existing portal services use the same selection algorithm as the read-only planner. This is not acceptance of native image decoding, image review, media/stock authority, full group expansion or a future media adapter.

## Service contract

| Function | Purpose and prerequisites |
| --- | --- |
| `prepareGalleryUploadEntry(imageDataUrl, thumbDataUrl)` | Existing early `decodeProductImage` validation and upload endpoint's optional-thumbnail truthiness. Returns the existing portal entry shape. |
| `planProductGallery(read, productId, requested, current, projection?)` | SELECT-only existing layout/selection/dedup logic. `current` is trusted server-loaded detail for this existing product and mode, never model-provided allowed IDs. Returns an internal binary plan. |
| `planGalleryImageAddition(read, productId, preparedEntry, mode)` in `products.js` | Existing upload endpoint's product existence, gallery role and main-image guards, current detail and common layout planning. Takes an entry from `prepareGalleryUploadEntry`. Lives beside `getProduct` to avoid a cyclic import. |
| `requireMainImageRemoval(current, decodedImage, galleryChanging)` | The existing pure main-removal guard, mechanically shared with `patchProduct`. A main-only removal must not strand a nonshared gallery. Explicit gallery edits retain their existing later selection validation. |
| `applyProductGalleryPlan(store, plan)` | Trusted internal mutation phase. Resolves new content refs to server-generated UUIDs/timestamps, then performs the existing delete/reinsert/layout update. Requires the same current-state transaction as planning; this low-level helper does not own authorization, revision advancement or domain history. |
| `saveProductGallery(...)` | Existing service entry; now calls the common planner and application phase. Existing callers retain their transaction, revision and history handling. Future commits must keep the existing high-level business/history wrappers rather than treat an internal plan as write authority. |

A plan contains `productId`, `role` (`single`/`holder`/`variant`), `holderId`, effective `mainDigest`, ordered `selected` refs, `retained` and `pending` Maps. Maps include private binary data/thumbnail data for the actual business write. They are **not JSON/MCP proposals or receipts** and must never be serialized into an approval envelope, client output or log. Future adapters must project only bounded trusted metadata/content refs for human review and rederive the private plan at commit under their current authority/revision fence.

Existing upload/static/main IDs retain identity. New bytes use deterministic internal `upload:sha256:<digest>` refs, with a deterministic suffix if a legacy stored ID already occupies that alias. Caller-assigned future UUIDs are unnecessary. Application allocates actual new UUIDs/creation timestamps; existing IDs, bytes, MIME, thumbnails and creation timestamps are preserved. New allocation happens at application rather than during read-only planning. No speculative INSERT, savepoint or rollback “dry run” is used.

The planner normally reads the current effective main bytes. Portal `updateProduct` already calls layout save **after** its main/metadata patch. A future SELECT-only combined main/layout preview can instead pass trusted `projection.mainImageDataUrl` (including explicit null) through the same existing decoder: dedup and main-presence checks then see exactly that proposed main without DML. This projection does not change tenant, role, listing membership or the portal's input contract. Main-only removals use the shared pure removal guard. Full product normalization, authorization, operation freshness, image checks and unsupported-field policies remain the caller's responsibility.

## Preserved inherited behavior

- At most20 requested entries and at most10 unique selected identities. Duplicate selections retain first order. Twenty duplicate main references can reduce to one;21 requests still reject. The layout is an explicit selection, not permission to fetch arbitrary image URLs.
- New upload bytes deduplicate by SHA256 against stored uploads and, for a single-product listing, the effective main. Main wins when bytes match. Distinct explicitly selected legacy IDs can still point to equal bytes; the extraction does not silently collapse those identities.
- Only the first new digest's thumbnail is decoded/stored. A duplicate of an existing/new/main image retains the prior thumbnail and follows the original ignored-thumbnail behavior. The upload endpoint's empty/falsy thumbnail omission remains unchanged; a directly supplied new gallery thumbnail still follows `decodeThumbnail`.
- IDs come from trusted current gallery/reference items and this product's stored uploads; another product's upload ID, another demo product's static ID and arbitrary URLs reject. Existing immutable demo references stay references, not copied uploads or network fetches.
- Holder selection remains earliest listing member by `created_at, sku, id`. A shared gallery contains uploaded/static entries and ignores `main` layout entries. A variant's distinct own main is separate: ten shared images plus that main can display eleven images. This must not be tightened to ten visible images.
- Existing `addGalleryImage` rejects nonholder variants and missing main. Existing `updateProduct` continues to ignore gallery fields on ordinary variant edits while retaining permitted metadata/image edits. The low-level layout planner reports role and preserves the old selection semantics; it is not a new MCP permission gate. A future adapter must reject unsupported variant fields without tightening portal behavior.
- Main-removal guards, explicit clearing, shared-gallery migration, holder/membership logic, public visibility and legacy image-only replacement behavior retain their existing services and transaction boundaries. Metadata/binary/layout changes still roll back together on validation or write failure.

## Validation and future acceptance

New synthetic SQLite/PostgreSQL tests run planners behind a SELECT-only facade and compare complete product/listing/gallery/history row digests before/after planning. They compare planned order/content identities against actual portal persistence, old identity/creation/thumbnail preservation, deterministic new refs and a real legacy alias collision. Other cases cover known static references, cross-product rejection, original request/selection caps, shared10+own11 visibility, variant add denial/update ignore, projected main dedup/removal, main-only guards, invalid uploads, forced insertion rollback, explicit all-image removal and actual CSV metadata updates retaining binary/gallery membership.

Existing gallery/product/options/listing/import/PostgreSQL compatibility tests remain the source of baseline behavior; no duplicate selection algorithm is added to tests. The current `decodeProductImage`/`decodeThumbnail` signature/base64/size validation is reused unchanged. Full native decode, decompression/pixel budgets, portable codec and trusted old/new image review are separate work and are not established by this extraction. Internal binary reads are intentional for exact digest planning; a future MCP transport must independently enforce byte, resource, staging, freshness and human-review bounds without leaking these rows.

No dependencies, schema, stock/order rules, MCP server/tool, external service call or production action are introduced. Reverting this extraction requires no data migration; already committed portal media changes remain real business state and are not undone by reverting source. Independent integrated source review and relevant regression acceptance remain required before a later media adapter uses these helpers.
