# Rollback plan

These requirements apply to the separately owner-authorized [production activation](13-PRODUCTION-ACTIVATION.md); live activation remains pending integrated acceptance and release. The accepted `b134f5c` [default-OFF release](12-LIVE-RELEASE.md) already installed shop schema 34/platform2. This activation proposes no new schema change. [Production recovery](PRODUCTION-RECOVERY.md) is the detailed operational runbook; source policy alone does not prove a coordinated live recovery.

1. Block this project's ingress and drain every backend writer before recovery, database restoration or epoch rotation. Preserve incident/audit evidence and inventory affected shops, instances, schemas and the accepted backend/codec/configuration tuple. Filesystem rotation and database commit are not atomic. Do not erase operation/audit records or undo committed commerce to make rollback look clean.
2. Use one coherent configuration: full production requires all MCP/v2/media/full CREATE/UPDATE flags, the named profile and every prerequisite. A partial production profile fails startup rather than falling back to MEDIUM. For disabled recovery, clear the profile selector and turn all v2 flags OFF; the initial old-binary fallback explicitly forces MCP OFF. Legacy reads may reopen only under an independently verified compatible disabled profile. Default OFF requires no epoch, codec identity, supervisor or generation mount.
3. Preflight the exact immutable backend/codec tuple, installed source/helper policy and capacity for forward plus rollback generations before stopping the accepted service. The trusted root controller/supervisor uses the shared update lock and durable pause/pending state. Prepare a fresh sealed token/socket generation, recreate all backend runtimes with read-only generation/epoch-directory mounts, and verify actual image/configuration/mounts plus database/epoch/codec private readiness before reopening frontend ingress. Never unseal/restart an old generation or reuse cached token configuration. Failed bounded same-build recovery stays paused/manual; first old-binary fallback writes durable quarantine and cannot implicitly resume enabled MCP after poller restart.
4. Binary rollback rotates the external canonical epoch after all writers stop and before authority reopens; normal forward activation and same-build codec recovery retain it. Old processes reread authority/final-writer fences and never adopt the replacement. Rebuild all runtimes against the new epoch. A rollback must restore a matched backend/codec/configuration tuple; image-only fallback under enabled flags is invalid. Preserve QR/AI settings and unrelated PostgreSQL/gateway services.
5. A database restore additionally requires the coordinated authorized backup set, explicit reconciliation of post-backup business writes, and invalidation of restored seller sessions/OAuth authority for every affected shop. Complete both bounded account and unbound-request phases. Epoch rotation alone does not invalidate restored legacy credentials/passwords. The recovery CLI leaves password hashes/account state unchanged; require an out-of-band trusted owner password reset through the existing service before reopening. Binary rollback without database restoration does not require unrelated credential resets or data undo.
6. Validate schema/storage/tenant identity, representative approved reads, stock/order state, audit and current artifact/readiness/privacy before resuming. Retain operation receipts/policy and 90-day audit evidence to their original horizons; bounded cleanup can run with MCP OFF/worker absent against existing schema 34 without DDL initialization/migration. Report any data loss, reconciliation or manual blocker accurately.

A schema 34-compatible binary is required even with MCP disabled; flags cannot downgrade schemas or disable the shared all-writer stock ledger. Local isolated rollback may revert/discard source without touching production. Non-production full CREATE/UPDATE flags remain independent: disabling one denies its pending full proposals and restores the corresponding safe constructor profile; enabling a different profile never reinterprets a pending proposal. Production requires the complete profile. Committed image restoration is a new explicitly reviewed business operation, and initial creation/upload/publish are separate approvals. Historical synthetic restore, exact-once stock/order and image replacement/restoration evidence is in [validation](10-FINAL-VALIDATION-REPORT.md); current lifecycle/artifact/live evidence belongs in the activation record.
