# Rollback plan

No deployment or migration is authorized by this document. These are requirements for a future reviewed release.

1. Immediately disable the new operations feature and deny all new scopes/commit endpoints; leave the existing read-only connector available only if independently safe. Verify every instance and queued job respects the flag. Revoke affected write grants and sessions if compromise is suspected.
2. Stop writers and background processors before any database recovery. Preserve incident evidence and audit, and inventory all tenant databases and versions. Do not erase operations or audit history to make rollback appear clean.
3. Prefer a tested binary compatible with the migrated schema and with the operations feature disabled. The current isolated schema is 34; binaries accepting only older versions cannot open it. Disabling MCP does not disable the new all-writer stock ledger; keep it with a compatible binary. Flags cannot change this version boundary. Preserve stage reservations until bounded cleanup removes all source/canonical bytes, and retain minimal policy/receipt evidence to its original horizon. See [media storage](MEDIA-STORAGE.md). Removing helpers does not undo committed commerce changes.
4. If a full restore is required, restore the coordinated encrypted backup set under an authorized runbook, account for post-backup business writes and reconcile them explicitly; avoid selective table copying that can break audit, foreign keys or tenant boundaries.
5. Invalidate restored OAuth grants/approvals as needed: a database restore could otherwise resurrect revoked credentials or previously consumed approval. Recheck server origin, tenant, account and grant bindings before restart. Actual synthetic SQLite/PostgreSQL snapshot restores verify a new external epoch rejects restored v2 authority. Production backup-domain separation, epoch provisioning and coordinated multi-instance drain/rotation remain unverified.
6. Validate schema, foreign keys, representative synthetic/approved tenant reads, correct stock/order state and audit, then restore traffic through an authorized change window. Report data loss/reconciliation, ownership and verification.

Local development rollback: discard the isolated branch or revert its changes; no production artifact is involved. For future migrations, a feature flag alone is **not** a schema downgrade. Test actual restore and compatibility before any release.
