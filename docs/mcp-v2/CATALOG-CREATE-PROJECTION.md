# Private CREATE media state and projection

`readCatalogCreateMediaMetadata(read, { normalizedInput, creationIdentity })` reads current catalog facts. It performs COUNT/SUM/MAX UTF-8/JSON preflight across all catalog, listing, category, option and company-currency dependencies before materializing any text. Its current-state revision changes when validation facts change, including inactive dictionaries and occupied IDs; it does not adopt a different creation plan. Input must already satisfy the product input normalizer, including an explicit currency. Images, stages and unknown fields are rejected.

`readCatalogCreateMediaState` then uses `preparePlannedProductCreate` with the absent non-null server product ID, the exact listing plan and the shared option-review formatter. AFTER includes actual adopted listing text and resolved options/variant label. The returned source is either `EXISTING_TARGET`, with a real oldest-member anchor and complete media snapshot, or `EMPTY_BEFORE`, which explicitly represents absence and is not a database snapshot. Empty existing listings are rejected. The joint product cap includes the new product: a target may contain at most 299 existing members.

The catalog metadata budget is 8 MiB with complete source preflight; B1's independent metadata and 16 MiB physical budgets still apply. Existing asset content limits are checked by the shared snapshot reader after bounded hashing. Physical byte preflight includes thumbnails before body loading. No stage or new image bytes are involved.

`projectCatalogMediaCreate(read, captured)` rechecks the complete private captured state and uses the existing B2 model, visibility and sharing kernels. It returns physical BEFORE/AFTER, actual visible views, exact DB source metadata, gallery-copy/layout effects, adopted new-product metadata and options. New product metadata has `before: null`. A new product's preview does not invent a `createdAt`: real creation computes a time strictly after all target members. Database ordering determines old members; the new ID appends after them, preserving the actual gallery holder.

These APIs require the caller's platform and tenant fence; they do not authorize, write, persist an operation/frame, register tools or activate reserved catalog policy. Private visibility data is not human approval evidence. The source-owned future CREATE pair must use both `catalog.write` and `media.write`, capability `catalog.write` and HIGH risk for ordinary private, fresh-group and existing-group cases alike. No lower-risk fallback is supplied here.

CREATE manifest assembly and a shared protected catalog review grammar remain separate work. They must bind literal BEFORE/AFTER labels/options and real visible images, support null-before product/listing effects, require page ACK even for zero assets, and preserve existing minimal receipt replay without rereading purged resources. Existing stock adjustments remain the separate HIGH inventory flow; initial CREATE stock uses the original service.

`test/catalog-create-media-projection.test.js` compares private projection against actual planned creation, including physical assets/thumbnails, visible gallery roles/order, adopted metadata, options, absence races, rollback and complete bounds on SQLite and PostgreSQL. These fixtures are business/integrity tests, not an OAuth/browser approval claim.
