## Security and performance

The hash/epoch tests cover stable JSON ordering, changes to every bound field, literal prompt-injection text, invalid types and ambiguous Unicode, size/depth bounds, hash mismatch, malformed envelopes and synthetic epoch rotation. The experimental DDL and authority tests cover default absence, explicit consent, current role/token/grant binding, repeated creation, constraints, uniqueness and rollback on both databases; no application migration uses that DDL. Isolated approval/engine tests use a synthetic adapter to cover session/password/CSRF, tampering, replay, concurrent commits, role and grant changes, expiry and audit rollback. A synthetic two-database PostgreSQL test observes an independent process waiting to suspend the platform tenant during a tenant commit, and rejects an approval after suspend/resume. Additional independent-process tests observe the application advisory lock for grant revocation, account disable/role downgrade and session deletion against commit; these protect only writers that use that lock and do not prove behavior for direct privileged SQL. A local browser test renders the review page against a mock at 1280, 390 and 320 pixels, checks that injected text stays inert and verifies explicit approval/rejection. None of this proves an application-integrated flow or a real commerce commit. Existing MCP tests cover their original OAuth and tenant security. A source scan found no direct HTTP fetch, shell execution, environment access or logging calls in the new backend helpers; their database adapters can use network connections. This is not an independent static security audit.

A local microbenchmark performed 10 warmups and 100 SHA-256 envelope hashes with a synthetic 60,000-byte description: p50 **0.094 ms**, p95 **0.178 ms**, max **0.769 ms** on this host. It is a single-process helper measurement, not a concurrent load test, query benchmark or production capacity claim. Application-integrated browser approval E2E, real-domain operation concurrency, SQLite/PostgreSQL v2 application migration, staging/restore rehearsal and independent security review are **NOT RUN**; the relevant integrations are not yet complete.

## Findings and readiness

- **P0 blockers for v2 writes:** approval UI, engine and platform lifecycle guard are not connected to authenticated application routes; no real business adapters, OAuth scope-consent flow, integrated migration or audit cleanup exists. The guard's synthetic separate-process test is not an application-integrated or multi-instance/restore proof. Prototype epoch/build fences have no verified external provisioning, artifact identity, coordinated restore or multi-instance rollout; idempotency retention and proposal-data minimization are unresolved. Lock ordering and privileges that prevent bypassing the store writer lock need review. No new write tool is enabled.
- **P1:** company/product revisions must cover all writers; sibling product timestamps do not advance when shared listing fields change; current image signature checking is not full decode verification; stock ledger and its coverage do not exist; current audit schema has fixed event/tool constraints.
- **P2:** conflicting old stock documentation should be corrected in a separately scoped change; current source confirms the 48-hour computed hold.
- **Unknown:** production artifact/flags, production migration and restore readiness, external client compatibility and independent security-review outcome. Production readiness is **NO**; staging readiness for v2 writes is **NO**. The isolated hash helper is development work only.
