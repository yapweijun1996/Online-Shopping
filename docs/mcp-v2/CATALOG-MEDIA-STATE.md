# Catalog/media current-state reader

C1b provides integrity data only. It registers no tool, authorizes no write, changes no schema or feature flag, and implements no AFTER membership/options/media projection, native decode or seller approval. Callers hold the current platform lifecycle fence followed by the tenant transaction; this helper never selects a tenant/store or grants permission from its result.

`readCatalogMediaMetadata(read,{productId,changes,plannedIdentity})` returns null for a missing existing product, otherwise frozen private current metadata, selector/predicates and a catalog revision. `changes` is a trusted server-normalized existing metadata PATCH. Closed schema and existing pure product-input normalization are checked for exact equality; raw input is rejected rather than silently normalized again. Stock, image, gallery, authority and caller listing-selector properties are absent. `plannedIdentity` is explicitly null or the exact C1a context. It is an identifier binding, not approval.

The current product derives its source listing. A real group change looks up the normalized target code; unchanged membership/SKU-only keeps the actual source, including private products. Source and existing target are deduplicated and jointly limited to300 products/two actual listings. Group members pointing into a third/missing listing fail409. A new/private target is an absence fact and remains absent; no ghost product/listing or UUID is allocated. Existing empty target listings are unsupported by B1 and fail closed.

Current source/target product/listing copies, descriptions, category records, company currency, option mappings and complete current/proposed type/value labels/codes/state/translations/order are bound. Existing SKU-conflict SQL is shared with `requireUniqueProductSku`; label conflicts use the existing SQLite NOCASE/PostgreSQL lower predicate. Target-code lookup/absence is explicit. A planned creation binds all four context fields, actual source identity, queried new UUID and its independent existing-or-null lookup. Merely including a random UUID in a hash cannot establish that it remains free. Occupation or source/code changes invalidate the revision; the reader never adopts the colliding row.

Omitted/proposed options remain literal facts. The reader does not derive AFTER option clearing, option labels or group mutation rules from `saveOptions`. A shared SELECT-only option-update preparer remains a prerequisite for a later catalog-media adapter. No readonly result may substitute for that service validation.

One CATALOG metadata budget covers both listings, every dependency table, intent and predicate framing. It never resets per listing/table/page. Actual database COUNT, UTF8 SUM and per-record MAX preflight every dependency before any complete long-text row is materialized. The conservative JSON bound uses six times UTF8 input bytes plus fixed nullable/key/scalar/record overhead, covering quotes, controls and Unicode escaping. Each record also has a64KiB bound; the cumulative catalog stream is8MiB. Actual per-record canonicalization/stream counting rechecks limits. Oversize returns controlled503 `CATALOG_REVIEW_TOO_LARGE`, without truncated fields, rows or raw TypeError. Some otherwise valid legacy metadata may conservatively reject.

Limits are300 product rows, two listings,1800 option mappings,1806 referenced current/proposed values/types,301 categories and one currency row. Dependencies are restricted by actual source/target IDs and current/proposed references. Parent category drift is included; exceeding the conservative category cap rejects rather than dropping a parent/proposed record. Metadata pages are at most200 rows. Fixed table/ID ordering and length-prefixed canonical records keep the digest independent of page boundaries. Stock and `updated_at` are retained from existing catalog column contracts, so a stock-only change may conservatively conflict; this never creates a stock PATCH or inventory write.

`readCatalogMediaState(read,sameInput)` runs that metadata preflight/collector first, then B1 `readMediaUnionSnapshot` for exact actual source/target physical content. Raw media revision includes hidden/unselected full images and thumbnails, labels, layout and member/holder ordering. Cross-component listing sets, product identities/labels/categories/layout/current main MIME and listing labels must agree; mixed snapshots fail409. B1 keeps its existing single-source version1 and true two-listing version2 semantics and exact source loader.

The unique composite is SHA256 of the canonical fixed object `{version:1,kind:'catalog-media-update',productId,intentHash,catalogRevision,mediaRevision}`. Future operation.expected_revision and manifest descriptor.graphRevision must BOTH equal that composite; no engine equality guard is relaxed. Keep raw mediaSnapshot/revision for exact physical loaders. Returned state is private and is not a public DTO or permission token.

The8MiB above is the ONE CATALOG metadata stream across source/target/dictionaries. B1 separately retains its existing8MiB media metadata and16MiB physical-content budgets. The two metadata representations together are **not** claimed to total8MiB. No global B1 budget companion or cap widening was introduced.

Tests use real SQLite/PostgreSQL services/stores and query instrumentation. They cover complete dictionaries/predicates, independent code/UUID absence,300/301 and200-row pages, cross-table cumulative budget when each table/row fits, UTF8/control/null and per-record limits before text/BLOB reads, hidden timestampless thumbnail changes, exact source/B1 tuple consistency, closed normalized arguments, private/same-source selection, dictionary/currency/legacy-copy/uniqueness changes and no allocation/writes. Frozen baseline comparison separately checks that safe catalog content hashes and descriptor objects are unchanged by the minimal shared exports/SKU predicate extraction. No projector, native/browser, engine or full catalog rollout acceptance is claimed by these tests.

C2 must separately hash-bind and human-display the B2 projector's actual `afterViews` visibility. Physical own-main content is not the same as visible own main: hidden-upload raw-byte equality can suppress it without deleting it. This batch does not add manifest fields or change DIRECT review state to hide that pending dependency.
