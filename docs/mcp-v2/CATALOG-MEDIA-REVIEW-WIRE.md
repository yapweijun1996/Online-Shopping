Exactly one new PRODUCT has `before: null` and `labels.before: null`; its AFTER has no own main and `ownMainVisible: false`. Every old product retains its listing, stored main and literal SKU/name. Exactly one target LISTING is included. Fresh/private creation has a null BEFORE listing and two effects with zero assets, still requiring at least one hashed page. Old aliases must be DB sources owned BEFORE; stages and new-product source owners reject.

Passing the fixed CREATE tool context permits the precise null BEFORE metadata. `catalogMediaReviewBinding` accepts CREATE's closed `{ toolName: 'catalog.preview_create', creationIdentity, baseRevision, reviewLabels, beforeViews, afterViews }`; BEFORE views contain only real old members, AFTER all members. Its existing bounded stream is reused with a distinct CREATE revision domain binding the strict D0 identity and `catalog/catalog` root. UPDATE hashes and DIRECT pages/root remain unchanged.

`assertCatalogReviewBinding` requires CREATE root `catalog/catalog`, HIGH risk, exact planned ID/listing, literal page/proposal labels and the matching stored final AFTER metadata. `optionReview` must match the final AFTER option pairs. This is integrity only; live dictionaries, service preparation, scopes, tenant and human evidence still require the future real flow. Final normalized request and resolved labels remain separate as described in [CREATE projection](CATALOG-CREATE-PROJECTION.md).

The shared renderer shows “Not yet created” for new-product BEFORE, literal AFTER labels and option names/values. Synthetic transport/frame fixtures do not establish actual CREATE authorization; real seller review/approval remains403. This preparatory contract supports reserved `catalog.preview_update` and `catalog.preview_create` / `catalog-media-v1` metadata grammar. It does not activate either policy. ## Complete labels and visibility

A catalog UPDATE PRODUCT effect has exactly `kind`, `productId`, `before`, `after`, and `labels`. Both product states exist and have exactly `listingId`, `role`, `mainAssetKey`, and boolean `ownMainVisible`. The main asset key describes the physical stored main image even when it is hidden. A null physical key requires false visibility. Labels have exactly `before` and `after`, each containing literal, well-formed `sku` (at most 40 UTF-16 units) and `name` (120 units). They are not trimmed or normalized by the wire layer.

LISTING states retain their previous grammar and may have one null side: a newly allocated listing did not exist before; a deleted source listing does not exist after. PRODUCT null sides, STAGE assets, stage references and nonzero new-upload bytes are rejected. All existing product effects, including unchanged members, appear in the sorted complete `proposal.reviewLabels` table. The table and complete proposal each have a 48 KiB canonical JSON limit. Oversize review metadata fails with 503 `CATALOG_REVIEW_TOO_LARGE`; nothing is clipped or omitted.

The trusted source of BEFORE visibility is `readCatalogMediaBeforeGraph`, which validates current SQL member tuples and database ordering before reusing the same private gallery graph as the projector. AFTER visibility comes from the projector's `afterViews`. Hidden physical uploads can suppress the own main through raw SHA equality; physical main keys alone cannot establish visibility. The browser displays the physical main separately from the actual ordered shopper gallery, with side-specific labels and safe text for nullable listings.

## One composite wrapper

`catalogMediaReviewBinding({productId, baseRevision, reviewLabels, beforeViews, afterViews})` returns frozen `{revision, reviewBinding}`. The binding is exactly `{version:1, baseRevision, reviewProjectionHash}`. Both view tables are sorted by product ID and cover exactly the existing label IDs. A view is exactly `{productId, role, holderId, visible:[{id,assetKey,shared}]}`; visible order is preserved, including private shared-main copy aliases. Functions, getters, holes, duplicate IDs, extra fields and foreign holders are rejected.

The projection digest is SHA-256 of a UTF-8 record stream. Each canonical JSON record is prefixed with its decimal UTF-8 byte length and `:`, then followed by a newline. The stream starts with `{version:1,kind:'catalog-media-review-projection'}` and then, in order, `reviewLabels`, `beforeViews`, `afterViews`: a `{table,count}` header followed by every row. Each record has a 64 KiB limit; one cumulative conservative 8 MiB budget covers the entire stream. It is not serialized through the envelope's whole-document node limit.

The final revision is SHA-256 of canonical JSON `{version:2,kind:'catalog-media-update',productId,baseRevision,reviewProjectionHash}`. `proposal.reviewBinding` carries the binding and `proposal.reviewLabels` carries the complete literals. `assertCatalogReviewBinding(envelope,manifest)` requires the operation expected revision and descriptor graph revision to equal this composite, the proposal descriptor to match the manifest, and every page's literal label to match the canonical stored proposal. Frame persistence and reads perform this comparison independently. The browser independently checks the outer composite and verified page literals. Fresh full state and projection checks remain the responsibility of future C orchestration; this helper grants no authority.

The raw B1 media revision, structure revision and exact seven-field sources remain unchanged byte-loader identities. Catalog metadata has its own cumulative 8 MiB source budget; B1 retains its independent metadata 8 MiB and physical 16 MiB limits. These are separate representations, not one combined 8 MiB promise.

`catalogMediaGraphBytes({beforeOldBytes,afterOldBytes})` validates both physical sides against 16 MiB and returns `{oldBytes:Math.max(beforeOldBytes,afterOldBytes),newBytes:0}`. This is the shared conservative manifest budget for C and future D, not a count of bytes read. Private projections retain actual before-read and after-copy-plus-thumbnail costs separately.
