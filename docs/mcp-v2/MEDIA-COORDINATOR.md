# Internal upload coordinator

This source batch remains internal and requires explicit development enablement. It registers no tool or route. All five media tools remain absent by default, production is rejected, and first-party media approval remains unavailable until actual image delivery, coverage ACK and trusted review UI are implemented and verified.

## Trusted interfaces

`createMediaCoordinator({store,binding,tenantGuard,epoch,buildDigest,codec,enabled:true,quickLogin:false,production:false})` captures trusted configuration. `codec` contains an absolute private socket path, local service token and configured artifact digest. A trusted test may inject `decode`; model input cannot select it. The fixed wire CODEC string validates the expected implementation contract; it is not remote attestation. The isolated local worker, launcher, sealed socket/token directory, trusted configured artifact and host remain in the TCB.

`begin(bearer,input)`, `append(bearer,input)` and `discard(bearer,input)` keep the transport bearer separate from model arguments. Every SQL phase obtains platform lifecycle fencing before the tenant writer and calls central `verifyMediaAuthority` with current persisted production setup, account/version/RBAC, token/grant, consent, epoch and tenant binding. No context field comes from model arguments. A new begin validates the existing product, full media graph revision, current slot/holder rules and server codec digest in the same atomic transaction as quota reservation; failure leaves no stage, quota or event. After fresh authorization, an identical existing begin returns its original minimal metadata even if the portal graph changed or upload expiry passed. It never renews expiry, restores bytes or supplies authority. Append cannot commit business data; final capture and sealing recheck the complete graph. Discard requires the original live context even when its product has since been removed.

Begin has exactly productId,targetSlot,expectedRevision,sourceSha256,sourceMime,declaredBytes,idempotencyKey. Append has exactly stageId,offset,dataParts. Discard has exactly stageId. Each of1–12 independently canonical base64 parts is1–4096 characters and decodes to at most3072 bytes; a call carries at most36864 bytes. No model string/body limit is widened.

A separate persistent APPEND class allows240 attempts per account/client/tenant per15minutes. Failed canonical chunks consume an attempt in a separate committed phase before the append writer phase. Unknown/malformed headers use the ordinary120 class. Each potentially successful attempt transfers at most36KiB, therefore all240 attempts transfer at most8,847,360 bytes (8.44MiB), below the nominal12MiB ceiling without a weighted table. Restart and concurrent calls share existing rate_limit_attempt rows. Future transport wiring must preserve IP300/shop600 and ordinary120, classifying only the exact fixed tool/action as APPEND; this module does not alter existing protocol limit selection.

## Single engine lifecycle

The returned server-owned `uploadAdapter` supplies capture/resolve/preview/persist/consume hooks to the existing operation engine. Capture under the authorized fence binds stage/product/slot/revision and takes a single45second lease clipped to upload expiry. It captures private bounded source bytes and old assets. Resolve runs outside both database locks, uses the engine's monotonic deadline, never starts a decode with less than5seconds remaining, keeps each call independently below5seconds, propagates cancellation and makes no automatic retry. The persistent stage allows at most two explicit validation attempts. Its total native-work budget is at most30seconds. Old and new bytes are checked through the same strict shared wire contract; source hash and MIME must match. All old captured content candidates may be validated conservatively, including hidden candidates that final canonical deduplication may select. No partial graph is accepted.

Final preview reacquires the fence and fresh authority, reads the complete current revision and calls the actual shared portal gallery planner with canonical image/thumbnail bytes. It derives all product/listing effects, filters unused old assets, and returns a canonical manifest separately from the small business proposal. Only the engine injects the verified media descriptor and owns operation/idempotency IDs, correlation, times and policy/frame persistence. The stage's original server correlation can seed the operation only after actual stage verification. No captured snapshot supplies live authority.

The final persistence hook rechecks the full graph and exact context before binding the lease. Apply reloads actual BOUND bytes under fresh engine context, validates the retained frame, runs the same planner again and compares the approved descriptor before calling existing trackUpdate + updateProduct/addGalleryImage services. It checks all resulting graph effects before consume/commit. Stock and prices are never copied from preview arguments. Existing history semantics remain unchanged (the legacy history helper records photo-count changes, not a fabricated text event for same-count image replacement); operation/media audit records remain atomic. Receipts contain only productId,listingId,revision, and committed replay must not require retained bytes or expired approval evidence.

Any successful-commit evidence fixtures in this foundation are synthetic internal review evidence only. They do not establish real human picture review, ACK coverage or browser approval. Actual first-party HTTP approval must fail closed while that interface is absent.
