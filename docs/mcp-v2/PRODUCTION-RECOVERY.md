# Production MCP recovery gates

A runtime's external epoch is a restore domain, separate from its shop database. Mount the containing `/run/mcp-control` directory read-only into the backend; do not bind a single file inode. Keep the epoch outside database backups. Configure its actual canonical absolute path: startup rejects both leaf and parent-directory symlink aliases (including `/var/run` aliases); use `/run/mcp-control/epoch`. This deliberate path tightening prevents caching an old alias target and does not change legacy v1 behavior. An operator replaces its canonical 32-byte base64url contents atomically during coordinated restore or binary rollback. A running process checks the current pathname at its authorization fences and rejects changed, missing, malformed or unreadable values. It never adopts a replacement epoch. Restart the reviewed backend with the new configuration before reopening traffic; previous consent and operation approval do not transfer to the new epoch.

Block ingress and drain all writers before rotating the epoch, restoring data or changing an incompatible image. Filesystem replacement and a database commit are not a single atomic transaction; repeated authorization checks do not remove this operational requirement. Native resolution occurs outside database locks and is checked again in the final writer phase. Configured production activation requires `TRUST_PROXY=1` for the reviewed HTTPS gateway topology; Origin, CSRF, current grant/RBAC and individual approval remain mandatory.

Database restore also restores old password hashes and legacy credentials. Before reopening, revoke restored OAuth authority and seller sessions through the host-only recovery workflow, and require an out-of-band trusted owner password reset through the existing password-reset service. Epoch rotation alone and `mustChangePassword` alone do not satisfy that password-reset gate. Recovery must not fabricate a password approval, automatically choose new passwords or silently disable accounts. Binary rollback without database restoration requires a new epoch but does not require unrelated credential revocation or data undo.

All commands and orchestration described here require trusted operator authorization. This source checkpoint does not install a timer, change a mount, rotate production credentials or demonstrate live recovery. Code eligibility is not human approval or hardware attestation.

## Packaged host maintenance commands

These commands use `readMcpMaintenanceConfig`: preserve real `NODE_ENV=production`, database/sealed tenant configuration and normal configuration validation, while explicitly disabling MCP and every v2 flag and removing production-profile/backend/worker selectors **only in this maintenance process**. No codec or epoch file is required and no worker is contacted. This reader is not an application activation path. The target must already exist at schema 34 with valid operation storage and matching tenant identity; maintenance does not create or migrate it. SQLite targets must be existing regular files; PostgreSQL opens the raw store without schema initialization.

- Existing single-shop cleanup: `node scripts/cleanup-seller-mcp.js 1 --tenant=default` (or an exact tenant UUID). The historical 1–1000 pass range remains.
- Dormant all-shop cleanup: `node scripts/cleanup-seller-mcp.js --all 1 --limit=20`. It visits only ACTIVE/SUSPENDED shops, at most 20 per invocation, at most 10 passes per shop. If `complete:false`, repeat with `--after=<nextCursor>` until complete, then reset the cursor for the next scheduled sweep. Each target's lifecycle and database identity are rechecked under the platform row lock before opening its store. DELETING/PURGED/other states never receive maintenance authority. A lifecycle race fails the invocation; retrying the page is safe. With no platform configured the all mode explicitly visits the default database once. Existing bounded transaction/byte cleanup and 90-day retention are unchanged.
- Restore invalidation, separately for **each affected shop**, under stopped ingress/writers: `node scripts/recover-seller-mcp.js --tenant=default --phase=accounts --limit=100`. Repeat `nextPhase` with `--after=<nextCursor>` when non-null. When the account phase finishes, invoke `--phase=requests` without a cursor and continue until `complete:true`. The final phase consumes unbound authorization requests. A successful account-page response alone does not mean restore recovery is complete.

Recovery pages contain at most 100 accounts or 100 unbound requests. Each account uses the existing credential service, which atomically revokes its entire OAuth family and sessions; this is an account bound, not a claim that all family SQL touches at most 100 rows. Existing INVALIDATE audit remains mandatory and faults roll back the complete page. Repeating an account page advances its auth version again, safely revoking again without creating grants, approvals or commerce writes. Password hashes, active state and must-change state remain unchanged: the trusted password-reset gate above is still required. Outputs are counts, phase/cursor and completion metadata only; failures use fixed messages rather than database details.

The packaged scripts do not start services or install scheduling. A host timer must keep its cursor privately, serialize its own invocations, use the existing trusted database credentials, and report failure/incomplete work. This checkpoint has synthetic SQLite/PostgreSQL CLI/service evidence, not a production restore or business approval.
