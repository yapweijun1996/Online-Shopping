# Planned listing creation identity

C1a is an internal business-service prerequisite only. It registers no tool, exposes no route/context field, changes no schema, and activates no catalog-media engine or approval policy. Authority, immutable review evidence and caller history remain separate responsibilities. The C adapter and B2 projection remain pending.

`applyPlannedProductUpdate(store, {id, changes}, context, mode='manual')` shares the same internal update implementation as ordinary `updateProduct`. `id` must equal `context.productId`. The context is exactly `{productId, previousListingId, targetCode, newListingId}`: lowercase UUID identities, a canonical uppercase group code or null, and a new ID distinct from the previous listing. Unknown context/input fields, symbols, accessors and nonplain context/input objects are rejected; the context is copied and frozen before any await. These are trusted server identifiers, not proof of authorization. Ordinary product input validation still rejects `newListingId`, `context` and other unknown PATCH fields. This entry excludes stock and image/gallery edits.

The caller may allocate a server UUID for an immutable future proposal without inserting a row. Only an actual group change that requires a **new** listing can use this entry. The existing writer transaction rechecks the current product/source binding, normalized target code and fresh `planMoveToListing`. A target that now exists, an occupied new UUID, a changed source, a mismatched code/product or an unchanged group returns409 `LISTING_PLAN_CONFLICT`; it never adopts another target or falls back to a random UUID. Null code means a fresh private listing, not uniqueness among all null-code listings.

The existing listing INSERT receives that exact UUID. The existing product move, live source-emptiness recheck/deletion, shared gallery service and option validation/drop then execute normally. Original product `created_at` and stock state remain unchanged. Failure after INSERT, source deletion or later options work rolls back the entire transaction, including the new listing, metadata, history and any caller-owned transaction work. The service does not add hidden history; a future approved adapter must wrap it in the existing `trackUpdate` and operation audit transaction.

Ordinary Portal/CSV/service updates still use the original `updateProduct` signature and random listing IDs, target adoption, validation, gallery, option and inventory behavior. No global or asynchronous identity context is introduced. The optional identity passed internally from products to listings is not an HTTP/model parameter. Callers using the low-level listing service continue to own the enclosing writer transaction.

Both SQLite and PostgreSQL tests compare planned and ordinary service behavior, assert no preview allocation, exact IDs and source cleanup, sibling retention, target-code/UUID/source conflicts, closed bindings and seller HTTP rejection, post-INSERT/DELETE rollback, option failure/drop, stock ledger invariance and caller history. No complete catalog-media/native/browser acceptance is claimed by this foundation. Production activation, full catalog policy, newborn products, staged media composition and stock mixtures remain outside this batch.
