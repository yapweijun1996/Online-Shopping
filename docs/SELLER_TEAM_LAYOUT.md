# Seller Team list and account drawers

Implemented from main940c425 for the approved Team redesign. This document describes source behavior; local fixture evidence and actual live acceptance are separate.

## Interface and existing account contract

The Owner-only Team page starts with a member list instead of a permanent Add form. The Team content is fluid within the existing Seller main gutter; it adds no max-width or auto-margin centering. At1920px the main content starts at292px and spans1584px (248px sidebar plus44px main gutters). The previous double-centering failure started at484px and limited Team to1200px. Layout tokens and ownership are documented in UI_SPEC.md and the existing public/shop/tokens.css source. Add person is a normal-flow action in the existing outer heading, using the opt-in shared ui-page-heading primitive. The description/actions are removed on Team disposal; other routes retain their existing heading behavior. Username, Role, Status, Last sign-in and Actions are separate desktop columns; small screens use cards. A never-used account says Never signed in. The Owner row is protected and exposes no mutation controls. No current-account badge is inferred from an Owner role. An accessible local Owner-help disclosure explains the existing Account → View profile → Change password path; it adds no reset authority or duplicate credential UI. On mobile the protection explanation occupies its own line, separate from the last sign-in timestamp. Help is collapsed by default beside this explanation, usable by keyboard/touch and local Escape, with no permanent guidance footer.

Username search, Role and Status filters run locally over the existing complete account-list response; the API is not newly paginated or bounded by this change. All members is the default. The desktop filter group stays concentrated on the left: search targets400px (maximum480px) with a localized placeholder, and Role/Status each use160px controls with12px gaps. These and13/14px type consume shared DS tokens. A360px compact search basis through1200px keeps Role/Status together. Compact table columns through1200px preserve a readable flexible username column when the sidebar opens. Phones use a full-row search followed by Role/Status together. Team labels, table headings, result counts and protection text use readable13px secondary type. The default count gives the total number of members; filtered results distinguish matching from total. Whitespace-only search is not considered a filter. Filters remain after successful operations. A newly created or changed member is highlighted; when filtered out, feedback explains how to clear filters. The existing latest20 account events remain in a secondary Member activity disclosure, labeled with the number of returned recent records (not total historical activity) and the actual latest event timestamp when available. A zero-record disclosure shows a localized no-activity message. Activity is structured as Time / Actor / Member / Action with a semantic table and mobile stacked records. Only existing event fields are shown; raw detail, passwords, hashes and internal action enums are excluded. Unknown future action enums show a localized Account updated fallback. No before/after values are invented; no timestamp is fabricated when no valid event time exists. Chinese canonical wording uses 店主 / 经理 / 员工, 添加成员, 最近登录 and 成员操作记录; the shared original roleOwner key also updates the existing profile role label.

Add person, Change role and Reset password use a shared accessible modal as a480px right drawer, full width on small screens. Only Manager/Staff are assignable. Username validation matches the server ASCII regex: first character is a letter/digit, followed by letters/digits/dot/underscore/dash,3–64 characters total. Temporary passwords use12–256 characters, cannot contain the username case-insensitively, and cannot repeat one character throughout. These checks assist the user; backend validation and authorization remain authoritative.

Staff fulfil orders and reply to chats; Managers additionally manage the catalog, decide sales orders and read sales figures. Neither role manages people or company settings. Existing account/session/OAuth business rules remain unchanged: role changes take effect on the next request and revoke OAuth authorizations without ending all browser sessions; deactivation and password reset end the member's sessions and revoke OAuth authorizations; reactivation does not restore previous sessions or grants. Reset passwords require first-sign-in change. No delete, invitation, email, owner recovery or credential persistence feature is added.

## Feedback, drafts and security

Failed writes preserve drawer inputs and show inline errors. Pending mutations disable inputs/actions and have duplicate guards. Successful writes close and clear credential fields, then reload the list. Failed refresh keeps old rows with an explicit stale warning and Retry, separately from the successful mutation message. The page/session identity and request sequence reject detached results. Owner page routing and backend security boundaries remain unchanged.

All drawer close surfaces use the existing draft guard and focus trap. Closing removes the dialog; disposed pages remove credential inputs. Team-owned confirmations use an optional AbortSignal on the shared confirmModal helper: disposal removes the top layer and resolves cancellation false. Existing callers without a signal retain their behavior.

Temporary passwords opt into non-secret revision signatures using data-private-draft and data-private-draft-revision. The shared update guard serializes only this marker/revision for opted-in controls, including when Show password changes the input type to text. Team's own guard identity is a monotonic edit revision, never a password. Ordinary forms retain existing signature behavior. Passwords are not placed in URLs, storage, summaries, account history or status messages.

## Verification and limits

Targeted tests cover account/session rules on SQLite and optional disposable PostgreSQL, private-draft signature redaction, the shared confirmation lifecycle, and real Team browser flows at390/768/1280/1920px under OS light/dark preferences, plus1050/1051/1100px sidebar-boundary geometry/long-username regression checks. CSS125% zoom reflow is checked separately and does not claim native device/PWA zoom certification. The current application has no actual dark theme; OS dark compatibility is not dark-theme acceptance. Browser checks cover one Owner, multiple/long usernames, filters/no matches, first-load delays/failures, drawer validation/focus/Escape, duplicate/error/pending writes, role/reset/deactivation/reactivation, hidden creation, stale refresh recovery, locale, navigation/session disposal and existing collapsed-sidebar tooltips. The focused polish browser tests additionally verify Chinese desktop/mobile layouts, main-gutter/normal-flow heading alignment and collapsed-sidebar behavior, compact filter geometry, whitespace/default/filtered count copy, the actual profile/change-password open/cancel path without writes, activity field semantics and future-action fallback. The full root application test suite is intentionally not run for this task.

Screenshots/logs are external artifacts. Fictional disposable browser checks do not establish authenticated production acceptance. The release manager separately verifies deployed identity/public assets and must report any owner-session live checks as verified or unverified. No real production account or password is mutated merely to manufacture evidence.
