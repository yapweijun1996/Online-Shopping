## Offline execution and persistence

`integration-requests.js` constructs deeply frozen, branded descriptors with a synthetic company/account binding, full input snapshot, fixed URL, JSON body, and no authorization header. The ledger accepts only these branded descriptors, verifies the current connection binding, and persists the complete request with the intent and outbox in one transaction. An altered stored URL, header, body, or policy fails reconstruction. Client/company identity is not inferred from provider payloads.

`integration-adapters.js` accepts only a branded, frozen fixture transport created from bounded plain JSON response data. Arbitrary functions, fetch objects, getters, and custom serialization callbacks are rejected. There is no live transport option or activation flag. Omitting transport returns `NOT_CONFIGURED` without leasing or transmitting. A future authenticated tenant adapter must supply the company context; this prototype is not an authorization service.

Provider acceptance persists a sanitized provider ID and `ACCEPTED` result atomically with `DONE`. It does not mean delivery. Ninja Van success requires documented HTTP 200; WhatsApp success requires an actual one-entry message array. Error titles, echoed addresses, contacts, message bodies, and raw provider responses are not stored in the result table. Verified rejection envelopes become `FAILED`; malformed successes, conflicts, throttling, server errors and network uncertainty enter `RECONCILE`. Ninja Van duplicate tracking code `109201` also reconciles when returned as HTTP 400; its numeric and string forms are normalized consistently. There is no verified provider idempotency guarantee, so the adapter never blindly resubmits these responses. Only an explicit synthetic `ABSENT` reconciliation permits the bounded retry. `FOUND` closes the operation without another submission. Concurrent attempts, stale leases, and late replies cannot finalize another attempt; a failed result write leaves the lease to expire into reconciliation.

Explicit opt-in and the text service window are checked when queuing a new intent and immediately before execution. A completed same-key replay recovers the stored fact even after the window closes, after rebuilding the request and verifying the current company/connection/account binding. An expired pending message remains pending and cannot transmit. Synthetic consent and template-approval fields stand in for trusted server records; revocation and current approval must be loaded from authoritative records before any live dispatch.

Status normalization distinguishes sent/accepted from delivered/read. Unknown values are quarantined as `UNKNOWN`; normalization never writes an order or payment status. The foundation inbox still uses **synthetic sequences**, not a fabricated ordering guarantee for real provider events. Signed raw-body ingress, event identity/correlation, timestamp conflict handling, and provider lookup/reconciliation contracts need a separately reviewed implementation before receiving real webhooks.
