# MCP image upload: secure-source review

Date: 2026-11-17. Inspected baseline: `1e4f973c31c00156fa7f44d53b3669e1b7575442`.

This is the earlier **external attachment resolver** review. The subsequent
requested direct HTTP upload implementation is documented separately in
[MCP_UPLOAD_URL.md](MCP_UPLOAD_URL.md). It issues a Shop-scoped upload capability
and never downloads an external URL; it does not assert ChatGPT attachment ownership.

**Readiness: HOLD.** The requested authenticated attachment resolver is not
implemented or configured. Do not enable Azure downloads, infer attachment
ownership from a hostname, or deploy a compatibility expansion on the evidence
available. This change adds regression coverage and documents the existing
fallback; it does not claim that the original attachment can now be uploaded.

## Root cause and execution path

oaisdmntprindiasocentral.blob.core.windows.net` is generated by the source-host
policy, after schema/Shop authorization and target preflight, but before DNS,
HTTP download, image decoding or stage creation. The hostname is diagnostic

## Missing trust mechanism

[`verifyMediaAuthority`](../src/mcp/operation-authorization.js#L94) establishes
the **Shop** tenant/account/client/grant context. It does not establish ownership
of an external ChatGPT attachment. `downloadFile(file)` receives no authenticated
attachment identity binding. `file_id` is shape-checked but never resolved
against a provider authority. The source SHA-256 is computed after download;
it protects the subsequent proposal, not the prior origin or owner of a file.

Repository searches found no authenticated `fileProvider.resolve`, provider
verification keys, attachment entitlement lookup, grant-bound file registry or
immutable provider attachment receipt. The documented [OpenAI file descriptor](https://developers.openai.com/plugins/reference#define-file-inputs)
contains download capability and metadata fields, not the server-verifiable
user/tenant/Shop-grant binding required by this task. This finding is scoped to
the inspected project and documented interface; it is not a claim that no other
provider integration could ever supply such evidence.

A URL query that resembles an Azure SAS is not verified here. A successful
storage response would demonstrate access using that capability, not ownership
by the current ChatGPT user or consent for this Shop grant. DNS existence, TLS,
the `oai` account prefix, filename and caller assertions such as `authorized:
true` are also insufficient. Azure's [account endpoints](https://learn.microsoft.com/en-us/azure/storage/common/storage-account-overview)
are account-specific in a shared namespace. Do not permit all Blob hosts, match
an arbitrary account prefix, or rewrite an unverified Blob URL into a trusted
hostname and call that authenticated resolution.

Before a resolver can be implemented, its real service contract must provide
authenticated issuer/audience, attachment entitlement, a mapping to the current
Shop grant context, bounded expiry, immutable content identity and revocation or
equivalent capability semantics. These must come from a trusted server-to-server
channel or verified attestation, never additional model-supplied flags. No stub
returning `authorized: true` has been added.

## Current controls and limits

| Area | Current behavior / limitation |
| --- | --- |
| Hosts | Source-owned direct OpenAI subdomain rule; Azure remains denied. The rule is not runtime-configurable. Configuration alone would not supply the missing attachment authority. |
| DNS and TLS | Validate every answer, reject prohibited addresses, pin the selected IP using `lookup`, retain hostname/SNI/certificate checks, disable connection reuse with `agent: false`. Tests cover mixed answers and mapped/alternate addresses; no claim of exhaustive independent IANA-range certification. |
| Timeout | Ten-second total deadline includes DNS, connection and response streaming. There is no separately configured shorter connect timeout. |
| Network policy | [`deploy/gcp/egress-guard.sh`](../deploy/gcp/egress-guard.sh) defines IPv4 Docker rules for RFC1918 ranges and the metadata IP. It is not a complete IPv4/IPv6 outbound allowlist. Installation/effective rules were not reverified or changed in this task. |
| Image limits | 524,288 source bytes and canonical bytes, 8,192 maximum side, 4,194,304 pixels, 81,920-byte thumbnail; native codec checks and full-pixel decode. HTTP MIME is not trusted. |
| Transformation | Existing fixed codec auto-orients, decodes pixels, strips metadata and re-encodes (including JPEG quality 100). This is the existing reviewed transformation contract, not a byte-preserving transfer. No new transformation was added. |
| Strict polyglot rejection | **Not satisfied for appended containers:** the native probe accepted valid PNG/JPEG/WebP with an appended empty ZIP, then omitted that suffix from canonical output. Canonicalization is not equivalent to rejecting the input. Do not claim all polyglots are rejected. |
| Cleanup | Downloader buffers are in memory; it creates no temporary files. Failed/aborted/timed-out transfers destroy the request and release permits. Durable stage cleanup follows [`media-maintenance.js`](../src/mcp/media-maintenance.js); do not delete audit data as cleanup. |
| Integrity and approval | Source hash/length protect staged input; canonical hash and manifest protect reviewed output. Existing seller approval and separate commit remain required. |

## Reproduction and supported fallback

1. Run the focused test command above. The reported hostname appears only as a
   negative diagnostic fixture, never as an allowlist exception. Tests use
   fictional data and make no real download requests.
2. In an authorized staging environment, obtain fresh `media.list` state for a
   disposable product. A direct MCP caller supplies the actual descriptor to
   `media.upload_file`; a path-based host wrapper must resolve its local file.
   Expect the unsupported Azure host to remain rejected with no stage/proposal.
3. If that client can read the exact image bytes, compute SHA-256 and length,
   then call `media.prepare_upload` begin with the fresh product/slot/revision.
   Split bytes into at most 36,864-byte append batches; split each batch into at
   most twelve independently Base64-encoded 3,072-byte parts. Use decoded byte
   offsets, never encoded character offsets, and verify every `nextOffset`.
4. Seal with the actual stage ID and a separate idempotency key. Success must
   return `PENDING_APPROVAL`, operation ID and a valid first-party review URL.
   Verify current media is unchanged and an unapproved commit is denied.
5. Review/approve separately; commit only after real approval, then read back
   media. Never fabricate image bytes, digest, review URL or approval evidence.
   If the host cannot access both file bytes and MCP calls, do not begin a stage
   that it cannot finish. Use a capable host or the authenticated seller editor.

## Release and rollback plan

The current work is reviewable local test/documentation changes. Do not push
them to `main` as a release: this repository automatically deploys CI-approved
main revisions. There is no new production artifact to roll back.

A future resolver release needs its actual provider contract, entitlement and
content-identity checks, adversarial tests, staging acceptance, independent
review, and explicit production authorization under the current task contract.
Use the existing CI-gated updater and immutable image records only after those
gates pass. Any future rollback must use the documented
[`PRODUCTION-RECOVERY.md`](mcp-v2/PRODUCTION-RECOVERY.md) controller/epoch/codec
procedure; do not copy old files into a running production backend or widen
download sources as an emergency workaround.

**Final decision: HOLD.** Root cause is demonstrated, the unsupported-source
denial and Base64 fallback are verified locally, but attachment provenance and
the original provider integration remain unverified. Strict appended-container
rejection is an additional unmet requirement. Neither missing gate is converted
to PASS by a successful synthetic upload or a working allowlisted URL.
