Keep the signed-in seller shell, teal identity, route, and seven existing locales (en, ms, zh-Hans, vi, th, ja, ko).

## Current form compared with the proposal

- **Desktop:** The current inline form already presents most fields in a two-column panel, but the list toolbar/context remains part of the same page, gallery continues below the visible viewport, and the only cancel control is in the form heading. The proposal gives the editor a clear return path and dedicated workspace, exposes the image/gallery context in a right rail, and puts Save/Cancel together. Keep both actions visible at 900 px height; if field validation or translated text increases height, use a compact sticky action row rather than hiding the actions.
- **Tablet:** No inline editor screenshot was supplied at 820 px; this comparison follows the current breakpoints. The sidebar becomes a drawer while the inline form remains two columns, but the list toolbar still shares the page and Save follows the image/gallery fields, so it can fall below the first screen. The proposal uses one editor surface with Save/Cancel in the heading row. Ensure translated labels wrap without colliding with actions; let actions move to a second row when necessary.
- **Mobile:** The current screenshot shows SKU, name, description, category, price, currency, and part of variants, but not Active, images, gallery, or Save. Users must scroll a long form to discover the primary action. The proposal keeps Save/Cancel fixed to the bottom safe area while the editor content scrolls; do not put controls under the bar, and add bottom padding equal to the bar plus safe-area inset. Preserve ordinary document scrolling—no nested scroll trap.

## Behavior and states

- **Loading:** On entry, show the editor shell and a localized loading status/skeleton for product data. Disable Save until the detail response is available. Keep Back to products usable. The current flow starts from a catalog row, paints its summary fields, then requests `GET /api/v1/seller/products/:id` to obtain detail/gallery data; expose that detail-loading state explicitly in the dedicated route.
- **Not found:** A 404 from the detail endpoint gets a localized “Product not found” state, with Back to products as the primary recovery action. Do not render a blank form or infer deletion.
- **Error:** Distinguish unavailable/network and server failures from 404. Retain entered values after a save failure, show an inline alert near the actions and field-level validation at the affected control, and focus the first invalid field. Existing validation includes required SKU/name/description/category, decimal price converted to minor units, valid currency, paired variant group/label, duplicate SKU/variant handling, and supported image type/size.
- **Save success:** Use an announced status (“Product saved”), keep the seller on the editor with the returned product values, and allow further edits. Prevent duplicate submissions while saving. Do not imply catalog publication or any external action.
- **Unsaved changes:** Preserve the existing dirty-change guard for Back, Cancel, route changes, and browser unload. For in-app navigation, prefer a localized confirmation dialog with Stay/Discard and initial focus on Stay; return focus to the initiating control on Stay. An explicit discard returns to products. Never silently drop edits.
- **Main image:** Show current image or an empty placeholder, preview selected replacements before save, and offer removal/undo removal. Accept PNG/JPEG/WebP up to 512 KB decoded. Removing the main image is blocked while gallery images remain; explain this beside the control and direct the seller to remove gallery images first.
- **Gallery:** Show gallery loading separately from an empty gallery. Gallery is available on saved products with a main image; allow up to four additional photos, uploaded individually through the existing API and removed individually. Show per-operation progress/error and announce completion. Disable add when there is no main image, main image removal is pending, or four photos exist. Removing gallery photos is immediate in the current implementation, so label that action clearly and do not pretend it is part of the unsaved form transaction.
- **Keyboard/focus:** Use a semantic form with associated labels, visible focus rings, keyboard-operable file inputs/buttons, and `aria-live` status/error text. On entry focus the page heading (or first field only after a user-initiated Edit action); after save announce success without unexpectedly moving focus. Sticky actions must not obscure focused controls or browser zoomed content. Respect reduced motion.
- **Long text/locales:** Keep description editable up to its existing 2,000-character limit and allow the textarea to grow/scroll without clipping. Wrap long names, SKUs, variant labels, errors, and localized labels; never widen the viewport. Use the existing seven translations rather than hard-coded English UI strings. The art labels stay an illustration annotation in review material only.

## Source behavior confirmed and limits

`public/seller/products.js` contains form population, client validation, dirty checks, focus handling, image preview/removal, gallery upload/removal, save/error mapping, and success feedback. `public/seller/index.html` defines the current form fields and inline product list; `public/seller/style.css` supplies a two-column desktop form, one-column mobile layout, and 44 px basic controls. `public/seller/app.js` guards unsaved form state on browser unload and seller navigation. `src/app.js` serves authenticated seller detail with 404 on missing IDs, supports PATCH saving, GET image bytes, POST gallery images, and DELETE gallery images. `src/products.js` and `docs/API.md` confirm gallery maximum, MIME/size limits, validation constraints, and the requirement to remove gallery photos before the main image. The current UI removes gallery photos immediately and reloads gallery state when needed.

These are visual and handoff deliverables only. A dedicated route, client-side route restoration, explicit not-found view, sticky responsive actions, and richer loading/error states are recommendations; they are not implemented backend or frontend capabilities. The proposal does not establish a new API contract or change product/business rules.
